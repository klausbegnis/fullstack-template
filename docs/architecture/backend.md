# Backend architecture

FastAPI + SQLAlchemy 2.0 (async) + asyncpg + Alembic on PostgreSQL 16. One implemented vertical —
auth + users — that every future vertical is expected to copy the shape of.

## Layers and the request flow

```
HTTP request
  -> router            app/routers/*.py            path/query/body parsing, DI wiring only
  -> dependency         app/dependencies/*.py        composition root: builds the service
  -> service           app/services/*.py            domain validation, RBAC, TRANSACTION BOUNDARY
  -> repository        app/repositories/*.py        SQLAlchemy queries, .flush() only
  -> model             app/models/*.py              declarative ORM classes
  <- response envelope app/schemas/api/*.py         SuccessResponse[T] / PaginatedResponse[T]
```

Rules, each backed by an automated check:

| Layer | Rule | Enforcement |
|---|---|---|
| router | No import of `app.repositories`, `app.models`, `sqlalchemy`, or `app.core.database`; no `HTTPException` | AST-parsed by `tests/unit/architecture/test_layer_boundaries.py` |
| service | No import of `fastapi`; owns the transaction boundary; `__init__` has no defaulted parameters | `test_layer_boundaries.py` + `test_dependency_contracts.py` |
| repository | Constructor takes `session: AsyncSession`; `.flush()` only, never `.commit()`; never raises `APIException` | `test_layer_boundaries.py` |
| model | `Mapped[...]` declarative; every table pins `__table_args__ = {"schema": ...}` | `test_model_contracts.py` + `alembic check` catches drift |
| `app/dependencies/` | Only layer importing both `Depends` and service/repository classes; one `get_<x>_service` + `XServiceDep` alias per feature | Convention, mirrored across `dependencies/auth.py` and `dependencies/users.py` |

One `AsyncSession` is created per request by `app/core/database.py` (`get_session`, exposed as
`SessionDep`) and shared by every repository the request's service constructs — a request never
opens a second session.

## Where transactions commit

Every mutation goes through the single shared helper in `app/core/transactions.py`:

```python
async with transaction(self._session):
    ...
```

`transaction()` joins an already-open transaction (committing on success, rolling back on any
exception) or opens and owns a new one when none is in flight. This exists specifically to kill a
defect from an earlier version of this codebase, where the same commit/rollback contextmanager was
copy-pasted across six services with inconsistent defensiveness — a hand-rolled
`try/commit/except/rollback` block anywhere outside `transactions.py` is treated as a defect, not a
style choice. See `app/services/users.py::create_user`/`update_user`/`disable_user` for the
reference usage, including the case (`update_user`) where a `ForbiddenException` is raised *before*
entering the transaction, so an authorization failure never opens one at all.

## Alembic: schema-per-bounded-context

Every table declares its owning PostgreSQL schema via `__table_args__ = {"schema": ...}`. The
schema names are centralized in `app/models/db_schemas.py`:

- `infra` — infrastructure-owned objects; currently just Alembic's own version table
  (`infra.alembic_version`, set via `version_table_schema` in `alembic/env.py`).
- `iam` — the identity/access-management bounded context: `users`, `auth_sessions`,
  `auth_refresh_tokens`.

Adding a new bounded context means adding its schema name to `DOMAIN_SCHEMAS` in
`db_schemas.py`; `alembic/env.py`'s `include_object()` hook restricts autogenerate to exactly the
schemas listed there, so a model in an unlisted schema is silently excluded from migrations rather
than erroring — check `db_schemas.py` first if a new model's migration comes out empty.

`alembic/env.py` runs migrations async, refuses offline mode outright (`run_migrations_offline`
raises — this template always requires a real PostgreSQL connection), and creates the `infra`
schema itself before configuring the migration context. `models/base.py` sets a deterministic
constraint-naming convention (`ix_`, `uq_`, `ck_`, `fk_`, `pk_` prefixes), so autogenerated
migrations never depend on database-assigned constraint names.

`uv run alembic revision --autogenerate -m "..."` works, but leaves the
`# ### commands auto generated by Alembic - please adjust! ###` banner comments Alembic injects
into the generated body, which violate this repo's no-comments rule. The preferred path is
`uv run python -m app.commands.create_migration -m "..."` (`--empty` for a revision with no
autogenerated body), which runs `alembic revision --autogenerate`, strips those banner comments,
then runs `ruff check --fix` and `ruff format` on the result — no manual cleanup needed.

**Never edit a migration file that has already merged to `main`.** Add a new revision instead — a
diff that modifies an old revision is a defect, not a fix, since anyone who already ran it has a
diverging history.

## Response envelopes

Three shapes, all in `app/schemas/api/base.py`:

```python
SuccessResponse[T]    # {success: true, message: str, data: T | None}
ErrorResponse         # {error: {code, message, details}, request_id: str | None}
PaginatedResponse[T]  # {success: true, data: list[T], total, page, page_size, total_pages}
```

List endpoints must return `PaginatedResponse[T]` — `PaginatedResponse` used to be declared but
unused by every router in an earlier version of this codebase; `routers/users.py::list_users` is
now the reference implementation and the bar every new list endpoint is held to. Single-item
endpoints return `SuccessResponse[T]`. Two endpoints are deliberately unwrapped exceptions to this
rule: `POST /auth/login` and `GET /auth/me` return the resource bare (no envelope) — the frontend's
anti-corruption layer (`lib/api/envelope.ts::isSuccessResponse`) accounts for this explicitly.

## Error contract

Every error response is `ErrorResponse`, produced by one of three handlers registered in
`app/main.py` (`app/core/exceptions.py`):

- `api_exception_handler` — any `APIException` subclass (`NotFoundException`,
  `ValidationException`, `UnauthorizedException`, `ForbiddenException`, `ConflictException`)
  raised by a service, mapped to its declared HTTP status and a stable lower-case `code`.
- `validation_exception_handler` — FastAPI's own `RequestValidationError`, sanitized to
  `{type, loc, msg}` per error before being embedded in `details.errors`.
- `general_exception_handler` — anything unhandled, logged with a full stack trace, returned to
  the client as a generic `internal_error` 500 with no internal detail leaked.

Every error response carries `request_id`, populated from `request.state.request_id` (set by
`RequestIDMiddleware`, see below) and echoed on the `X-Request-ID` response header — the same ID
that appears on the structured log line for that request, which is how a client-reported error
gets traced back to server logs. Covered end-to-end by
`tests/integration/api/test_error_contract.py`.

## Observability

`app/core/middleware.py` registers two ASGI middlewares (in `app/main.py`, request-ID middleware
runs innermost so it wraps the handler and the access logger sees the bound ID):

- `RequestIDMiddleware` — takes the inbound `X-Request-ID` header if present, otherwise generates
  a UUID4; binds it into a `contextvars.ContextVar` (`app/core/request_context.py`) for the
  lifetime of the request, sets `request.state.request_id`, and echoes it on the response header.
- `AccessLogMiddleware` — emits one structured log line per completed request
  (`http_method`, `http_path`, `http_status_code`, `duration_ms`).

`app/core/logger.py` configures the root logger to emit single-line JSON
(`{timestamp, level, logger, message, request_id?, ...extra}`) via a custom `JSONFormatter`, and a
`RequestIdFilter` stamps every log record — not just the access log — with the request ID bound in
the current context, so grepping one `request_id` across logs reconstructs everything that
happened during that request. Verified by `tests/integration/api/test_observability.py` and
`tests/unit/core/test_logger.py`.

## Login rate limiting

`POST /auth/login` declares `dependencies=[Depends(rate_limited("login"))]`
(`app/dependencies/rate_limit.py`). Every attempt, successful or not, counts once against the
client IP (`login:ip`) and once against the normalized body email (`login:subject`); a request
whose body carries no usable email still counts per IP. Over either limit the route answers
`TooManyRequestsException` — a 429 with `code: "rate_limited"`, `details.retry_after_seconds` and
a `Retry-After` header — before the auth service runs.

The counters are fixed windows in `iam.rate_limit_windows`, shared by every worker and surviving
restarts. A hit is one atomic `INSERT ... ON CONFLICT DO UPDATE` (`RateLimitWindowRepository.hit`)
that restarts an ended window at 1, committed by `RateLimitService` on a short session of its own
(`request_session_factory`), so a hit still counts when the login later fails and rolls the
request session back. Only the SHA-256 digest of the email or IP is stored.

| Setting | Default | Meaning |
|---|---|---|
| `RATE_LIMIT_ENABLED` | `true` | `false` skips counting entirely (no database access) |
| `RATE_LIMIT_LOGIN_PER_EMAIL` / `RATE_LIMIT_LOGIN_PER_IP` | `10` / `50` | attempts per window |
| `RATE_LIMIT_LOGIN_WINDOW_SECONDS` | `900` | window length |
| `RATE_LIMIT_TRUST_FORWARDED` | `false` | key on the right-most `X-Forwarded-For` hop |
| `RATE_LIMIT_CLIENT_IP_HEADER` | empty | header a trusted edge proxy overwrites (e.g. `X-Real-IP`); wins over `X-Forwarded-For` |

Behind the Next.js server the API sees the frontend container as the peer, so the login Server
Action forwards the browser's `X-Forwarded-For` (`frontend/src/lib/auth/forwarded-headers.ts`);
enable `RATE_LIMIT_TRUST_FORWARDED` only when every request reaches the API through a proxy that
sets that header. Ended windows are deleted by
`uv run python -m app.commands.purge_rate_limit_windows [--limit N] [--dry-run]` (default limit 500;
prints the count); schedule it hourly. A new throttled route adds its policy to `_POLICIES` in
`app/core/rate_limit.py` — an unknown scope fails at import time.

## Security audit log

`app/services/security_audit.py::record_security_event` appends one row to `iam.security_events`
(`action`, `user_id` the event is about, `actor_user_id` who caused it or null, a JSONB `payload`,
`created_at`) and logs one `security event recorded` line carrying only the action and the user
id. It runs inside the calling service's transaction, so the event commits or rolls back with the
change it describes. Recorded actions:

| Action | Recorded by | Actor | Payload |
|---|---|---|---|
| `auth.login_succeeded` | `AuthService.login` | the user | — |
| `auth.login_failed` | `AuthService.login`, known account only, committed before the 401 | the user | `reason`: `invalid_password` / `disabled` |
| `auth.logout` | `AuthService.logout` | the user | — |
| `auth.refresh_token_reused` | `AuthService.refresh` when a consumed or revoked refresh token is replayed (the session is revoked) | null | — |
| `user.created` / `user.disabled` | `UserService.create_user` / `disable_user` | the admin | `role` on create |
| `user.updated` | `UserService.update_user` when name or email is sent | the editor | `fields`: names only, never values |
| `user.role_changed` | `UserService.update_user` when the role actually changes | the admin | `old_role`, `role` |

A sign-in for an unknown email writes no row (there is no user to attach it to); it logs
`login failed for an unknown account` without the address. `safe_payload` refuses any payload key
that names a password, secret, token, credential, cookie or email, so a careless caller fails
loudly instead of persisting one. `user_id` deliberately has no foreign key: the trail outlives
the account it describes. There is no read API; query the table directly or build an admin
endpoint on `SecurityEventRepository`.

## Unhandled-error alerts

`general_exception_handler` still returns the same sanitized 500, but when the process reports
alerts it also captures an `ErrorAlert` (`app/core/error_alerts.py`) and hands it to the reporter
on `app.state.error_alerts` as the response's background task, so delivery happens after the
body is sent and can never change it. `APIException`s and validation errors never alert.

- **Scrubbing.** The alert names the route by its template (`/users/{user_id}`, never the raw
  path), carries only the request id and the signed-in user's id (`request.state.user_id`, set by
  `get_current_user`), and renders the traceback from frame summaries alone — file, line,
  function, source line; never locals, headers, cookies, query or body. The exception message is
  cut before any `[SQL:`, `[parameters:` or `DETAIL:` marker, emails, phone-like digit runs and
  token-like strings are replaced, and it is capped at 300 characters.
- **Throttle** (`app/core/error_alert_throttle.py`, per process). The first occurrence of a
  fingerprint (exception class + route + innermost `app/` frame) is delivered; repeats within
  `ERROR_ALERT_REPEAT_WINDOW_SECONDS` (600) are counted and summarised once when the window
  closes. At most `ERROR_ALERT_MAX_POSTS_PER_HOUR` (20) deliveries per hour; the excess is
  dropped and reported in one notice when the hour turns.
- **Pluggable sink** (`app/core/error_alert_sinks.py`). `ErrorAlertSink` is a one-method
  Protocol (`async deliver(notification)`). `LoggingErrorAlertSink`, the default, writes one
  structured `error alert: ...` record. Setting `ERROR_ALERT_WEBHOOK_URL` selects
  `WebhookErrorAlertSink`, which POSTs `{"text": "<plain-text rendering>"}` — exactly the body a
  Slack incoming webhook accepts, and easy for any other receiver to consume. A failed delivery
  logs one `error alert not delivered` warning naming only the error type, never the URL. Another
  destination is a new class with a `deliver` method passed to `build_error_alert_reporter`.

Reporting is on only under `ENVIRONMENT=production`; in development the traceback in the console
is the alert. The reporter's pending flush task is cancelled in the lifespan shutdown.

## Enforcement mechanisms (why the rules above are real)

- `tests/unit/architecture/` is discovery-based, so a new feature is covered without a new test
  file: `test_layer_boundaries.py` AST-parses every router, service, repository and model for the
  import table in `.agents/rules/backend/layering.md` (plus `.commit()`/`HTTPException` bans);
  `test_dependency_contracts.py` resolves every `XServiceDep` to a service with no defaulted
  constructor parameters; `test_route_contracts.py` walks `app.routes` for an auth dependency,
  envelope return annotations, status codes, unique operation ids and static-before-parameterized
  ordering; `test_model_contracts.py` checks every table's schema pin; `test_migration_contracts.py`
  checks the single head and the enum recipe; `test_test_conventions.py` requires one unit module
  per service, one integration module per router, and fakes instead of `unittest.mock`.
- `.agents/hooks/guard_paths.py` (PreToolUse in both harnesses) refuses edits to migrations
  already on `main`; `.agents/hooks/post_edit_check.sh` runs ruff on every edited file.
- `uv run alembic check` fails CI on any drift between the ORM models and the migration history.
- `uv run mypy app` runs in strict mode (`tool.mypy` in `pyproject.toml`) across the whole `app`
  package.
- `uv run ruff check .` enables `C90` (mccabe complexity, max 10) and `PLR0915` (max 50
  statements per function) in addition to the default rule set — both size-limit guardrails,
  not just style.
- CI (`.github/workflows/ci.yml`) runs all of the above plus `pytest` against a real Postgres 16
  service container on every PR and push to `main`.
